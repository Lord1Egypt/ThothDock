## 2. The web-panel session finding (P1, fixed)

*Root cause.* `internal/panel/auth.go` persisted sessions in `sessions.json`
(30 days idle) and loaded them at every start; a unit test required exactly
that; the Android Stop button only killed the process and removed the pairing
code. A browser paired once therefore kept full control (start, stop, delete)
after the owner pressed Stop → Start.

*Policy now.* Browser sessions are valid only within one Web Panel server
lifecycle (process): they live in memory, end after 12 h without a request, on
logout, on "Disconnect all devices" (SIGUSR2 to the running panel: all sessions
and the pending code are dropped in memory and their event streams closed
before the panel announces a new code), and always when the process ends (Stop,
restart, crash, SIGKILL, Android recreation). A leftover `sessions.json` is
deleted at start; if that fails the panel does not start (fail closed). The
cookie has no `Max-Age`. The TLS certificate is untouched, so the fingerprint is
unchanged. A new pairing code alone does not revoke paired browsers; the
Android tab has separate Start/Stop, New code and Disconnect all devices.
Normal refresh, tab changes and leaving the Android tab do not call Stop.

*Proof.* Go tests with the race detector (restart rejects old cookie and CSRF and
every container action with 401, legacy file purged and not honoured, refusal to
start when it cannot be deleted, two browsers, revoke-all ends event streams,
pending code cancelled, logout ends only its session, 12 h idle expiry,
concurrent pair/revoke/check); `tests/panel/lifecycle.sh` with the real binary
(SIGUSR2, SIGKILL, restart, SIGTERM, legacy file, certificate unchanged; 21
checks; also a CI step); on the Samsung phone `tests/panel/device-lifecycle.sh`
drove the Android UI through the owner's exact sequence — pair, authenticated,
Stop, Start, reopen with the old cookie: **401 on the session, start, stop,
restart, delete and the event stream; fresh pairing 200** — and Disconnect all
devices with two browsers: **both 401 at once, event stream ended, panel still
listening, new code works, fingerprint unchanged**: 24/24
(`evidence/final-release/session-lifecycle/device-lifecycle.log`; codes,
cookies and CSRF tokens are never printed). The existing 22 panel security
checks pass again (`panel-security-*.log`). Only a disposable container
(`qa-disposable`) was started, stopped and removed; the owner's four containers
were not touched by these tests.

*Remaining limitation.* Anyone holding a live cookie (or the unlocked phone) is
trusted until Stop or Disconnect; the certificate is self-signed.

## 3. QA-07 — Android process pressure

*Mechanism (from the 2026-10-11 06:35:15 logcat and `dumpsys`).* Android's
`ActivityManager` logged "Killing PhantomProcessRecord ... libthothdock.so:
Trimming phantom processes"; the engine exited 137. `dumpsys activity
processes` lists "All Active App Child Processes": 22 records, all this app's
uid. So the engine was ended by phantom-process trimming, not by the low-memory
killer or a crash. Not established: the exact count at the kill, the cap on
this firmware (`max_phantom_processes` is null, so the AOSP default of 32 is
presumed; apps cannot read it) and whether other apps' children are counted.
The five-container experiment was not repeated.

*Mitigation (Process Guard).* See `ANDROID_LIFECYCLE.md`. On-demand counting
(no thread, timer or polling), levels with hysteresis, an estimate for created
containers, warnings through the Docker CLI's own channels, the Containers
screen and the Web Panel, never a refusal, and a recovery report. Verified: unit
tests for low/high/unknown/stale/hysteresis/burst/concurrency/no new
goroutines/no state change; on the phone `docker create` printed the warning
live at 22 processes plus one created container, the Containers screen showed the
banner at 24, the recovery report after `am force-stop` listed the four
interrupted and restored containers and the last observed count and claimed no
cause (`evidence/final-release/recovery-after-force-stop.json`).

*Disposition:* **MITIGATED — RESIDUAL ANDROID PLATFORM RISK.** A warning cannot
stop Android from ending the engine.

## 4. Security audit (targeted, Critical/High)

| Area | Result |
|---|---|
| Engine API | owner-only 0600 Unix socket; the development TCP listener only on loopback and only by flag, never set by the app; panel reaches the engine through a fixed allow list, not a proxy; the new `/thothdock/process-guard` is read-only on the same socket |

| Resource exhaustion | restart backoff to 60 s; event ring 1024; log rotation; extraction ceilings; Process Guard adds no background work |

## Network semantics (actual behaviour)

| Network | What it is | API |
|---|---|---|
| `bridge` | Compatibility mode: the shared Android device network, not a Linux bridge, no address range | labels `io.thothdock.network.kind=device-bridge`; connect/disconnect 403 |
| `host` | The shared Android device network | `device-host`; connect/disconnect 403 |
| `none` | Not implemented: `--network none` and connect are refused (501), never a silent fallback | `supported=false` |
| user-defined | Own 127.77.x.y address per container, names and aliases through `/etc/hosts`, outbound DNS/HTTPS | `user-defined`, range 127.77.0.0/16 |

Functional address separation, **not** enforced isolation: a container that
knows another container's address reaches it from any network (measured on
the phone; `SECURITY_MODEL.md` J).
